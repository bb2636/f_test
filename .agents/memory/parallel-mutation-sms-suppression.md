# 다건 상태변경은 클라이언트 병렬 mutate가 아니라 서버 단일 트랜잭션으로

여러 건(예: 접수취소 다중세대)을 한 번에 상태변경할 때, 클라이언트에서 같은 useMutation을
건별로 병렬 `mutate` 하면 일부만 성공하고 일부가 실패해 **상태 불일치**가 생긴다.
특히 보험사 통지 같은 부수효과가 이미 1회 발송된 뒤라면 화면 상태와 실제 통지가 어긋난다.

**해결 패턴:** 서버에 다건 처리 엔드포인트를 두고 `db.transaction`으로 묶어 전부 성공 또는
전부 롤백한다. 클라이언트는 `{ caseIds: string[] }`로 단일 호출. 실패 시 invalidate로 화면을
서버 최신 상태로 되돌리고 사용자에게 롤백되었음을 명확히 안내한다.
- 트랜잭션 안에서 행을 `.for("update")`로 잠그고, 없는 건이면 `throw` → 전체 롤백.
- 상태이력(caseStatusHistory) insert도 같은 tx 안에서 처리해야 일관됨.

## 병렬 mutation의 부수효과 억제(과거 접근, 단일호출로 대체됨)

병렬 mutate가 불가피할 때 onSuccess 부수효과(팝업/문자 재오픈) 억제는 **공유 ref 카운터**가
아니라 `mutate({ ..., suppressXxx: true })`처럼 **mutation 변수 플래그**로 건별 판단해야 한다.

**Why:** 공유 ref(카운터/불리언)는 성공·실패가 비동기로 섞여 settle될 때 경합이 난다.
- 첫 성공이 카운터를 깎고 플래그를 내리면, 이후 실패의 onError가 리셋 조건을 못 만나 잔량이 남아 무관한 다음 작업까지 잘못 억제됨.
- 반대로 실패가 먼저 카운터를 0으로 만들면, 늦게 도착한 성공 콜백이 팝업을 다시 열어버림.
변수 플래그는 각 호출에 고정 동봉되므로 도착 순서·성공/실패 무관하게 정확하다.

**How to apply:** 가능하면 단일 트랜잭션 엔드포인트로 묶을 것. 부득이 병렬이면 공유 useRef 상태에
의존하지 말고 mutation 변수 플래그로 분기.
