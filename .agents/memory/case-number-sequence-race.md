# 접수번호 순번 생성 경합 (case_number 23505 "접수번호가 중복되었습니다")

접수번호 = `날짜(YYMMDD) + 순번` (예: `260623001`). 순번은 **날짜 기준**이라
사고번호/증권번호가 전혀 달라도 같은 날 접수면 같은 prefix를 다툰다.

**근본 원인 (TOCTOU):** `getNextCaseSequence`는 advisory lock 안에서 순번을 *읽고*
잠금을 풀어 반환한다. 실제 `createCase` 저장은 그 뒤 별도 경로에서 일어난다.
"읽기→저장" 사이 틈에 다른(동시/연속) 접수가 같은 순번을 가져가면 두 건이 같은
`prefix-0`을 만들려다 23505 → 일반 핸들러가 "접수번호가 중복되었습니다" 반환.

**왜 -0에서 터지나:** `createCase` 내부 재시도는 **피해세대(suffix≥1)** 충돌만
자동 재배정한다. **-0(손해방지) 충돌은 재시도 없이 throw.** 처리구분 "둘 다"는
-0을 먼저 만들기 때문에 여기서 크래시. (손해방지-only도 동일.)

**Why:** 다중 사용자(보험 접수) 환경에서 거의 동시 접수가 흔해 경합 창이 자주 열린다.

**해결 패턴 (적용됨):** 신규생성 블록(POST /api/cases, status==='접수완료')을
재시도 루프로 감싼다. 매 시도 `getNextCaseSequence` 재호출 → 분기별 생성 → 성공 break.
`case_number` 23505 충돌 시 이번 시도에서 만든 건을 `deleteCase`로 정리(고아 방지) 후
새 순번으로 재시도. -0을 먼저 만들므로 -0이 성공하면 그 prefix는 우리 것 → 후속 -1 안전.

**How to apply:** 접수번호를 새로 만드는 다른 경로(임시저장 신규생성 등)도 같은
TOCTOU에 노출된다. 순번 생성+저장이 분리된 곳을 보면 동일 재시도/정리 패턴 적용.

**남은 한계:** 피해세대-only 신규는 -0이 없어 첫 건이 `-1`. 경합 시 `createCase`의
suffix 자동증가가 충돌을 "성공"으로 덮어 **다른 사고건이 같은 prefix에 잘못 묶일 수**
있다(크래시는 아님, 그룹핑 정합성 문제). 완전 해결은 순번 예약+삽입을 한 트랜잭션으로
원자화해야 함.
