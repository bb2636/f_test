현재 로그인 장애는 일회성 버그 수정이 아니라, 재발 방지 중심의 구조 안정화 작업으로 다뤄주세요.

이미 확인된 사실:
- LOGIN ATTEMPT 이후 VERIFY PASSWORD / LOGIN SUCCESS / LOGIN FAILED 로그가 찍히지 않는 구간이 있었음
- getUserByUsername() → getCachedUsers() 경로에서 DB hang이 발생했음
- users 테이블 조회가 SELECT * 구조였고, attachments(Base64) 컬럼 때문에 전체 조회 크기가 과도하게 커져 캐시 재조회, warm-up, direct fallback이 모두 같은 병목에 걸렸음
- DB 연결 불안정, cold start, 캐시 TTL 만료, 동시 로그인, 세션 조회 지연 시 전체 인증 흐름이 멈추거나 서버 재시작 루프에 빠질 수 있는 구조였음
- 로그인 후 기존 세션 확인(getCurrentSessionId), setCurrentSession, 로그아웃, /api/check-session 에도 타임아웃 누락 지점이 있었음

이번 작업 목표:
1. 로그인/세션/캐시/DB 연결 흐름 전체에서 무한 대기(hang)가 절대 발생하지 않게 할 것
2. DB 지연, connection terminated, cold start, 캐시 TTL 만료, 동시 다발 로그인, 서버 재시작 직후 요청 폭주 상황에서도 서버가 죽지 않고 최대한 정상 응답하게 할 것
3. 특정 쿼리 하나의 실패가 로그인 전체 실패나 프로세스 크래시로 번지지 않게 할 것
4. 이번에 드러난 시나리오 외의 유사 장애도 코드 기준으로 선제 차단할 것

반드시 점검/수정할 항목:

[1. 데이터 조회 구조]
- users 관련 조회에서 attachments 같은 대용량 컬럼이 불필요하게 포함되는지 전부 점검할 것
- 로그인/세션/인증 경로에서는 반드시 최소 컬럼만 조회하도록 분리할 것
- SELECT * 사용 구간이 있으면 전부 검토해서 제거 또는 제한할 것
- “목록/캐시용 조회”와 “인증용 단건 조회”를 분리할 것

[2. 캐시 구조]
- getCachedUsers, getCachedCasesRaw 포함 shared pending Promise 패턴 전체 점검
- usersCacheFetching / casesRawFetching 이 오래된 Promise를 재사용하거나 영구 대기 상태가 되지 않도록 보장할 것
- 캐시 실패 시 stale cache 사용 가능 여부를 검토하고, 실패 후 상태값 초기화가 반드시 되게 할 것
- 캐시 실패가 인증 핵심 경로를 막지 않게 할 것

[3. 로그인/세션 흐름]
아래 전 구간을 코드 기준으로 추적하고, 각 단계별 timeout / fallback / try-catch / 로그를 보강할 것:
- LOGIN ATTEMPT
- getUserByUsername
- verifyPassword
- getCurrentSessionId
- session.save
- setCurrentSession
- LOGIN SUCCESS / LOGIN FAILED
- logout
- /api/check-session
- 인증 미들웨어

[4. DB 안정성]
- 모든 핵심 DB 조회/수정에 timeout 적용
- pool / sessionPool 설정(connectionTimeoutMillis, idleTimeoutMillis, max)을 점검하고 보완할 것
- DB transient failure, Neon cold start, connection terminated 상황에서 fallback 또는 graceful degrade 하도록 수정할 것
- direct DB fallback도 timeout 없이 기다리지 않게 할 것

[5. 예외 처리]
- warm-up, background refresh, login, session, auth middleware, logout, check-session에서 발생하는 예외가 unhandled rejection으로 남지 않게 할 것
- 전역 unhandledRejection 핸들러가 있더라도, 각 호출부에서 먼저 try/catch로 처리할 것
- 서버 크래시 대신 401/503/안전한 fallback 응답으로 끝나게 할 것

[6. 시나리오 기반 재발 방지]
아래 시나리오를 하나씩 코드 기준으로 검증하고, 취약하면 수정할 것:
- DB 응답 지연
- DB 연결 끊김
- Neon cold start
- 캐시 TTL 만료 직후 동시 로그인
- 서버 재시작 직후 로그인 몰림
- warm-up 실패
- direct DB fallback 실패
- getCurrentSessionId 지연
- setCurrentSession 지연
- /api/check-session 지연
- 로그아웃 중 세션 정리 지연
- stale cache가 없을 때 첫 요청
- 빈 배열/빈 객체 반환 때문에 정상 유저가 없는 사용자로 처리되는 경우
- 대용량 컬럼 재유입으로 인증 쿼리가 다시 무거워지는 경우

[7. 로그/관측성]
- 각 단계에 구조화 로그 추가
- source(cache/direct/stale), elapsed ms, timeout 여부, fallback 사용 여부를 로그에 남길 것
- 다음 장애가 발생해도 로그만 보고 어느 단계에서 멈췄는지 바로 알 수 있게 할 것

[8. 결과 정리 형식]
수정 후 반드시 아래 형식으로 정리할 것:
1) 왜 이 장애가 다시 발생할 수 있는 구조였는지
2) 이번에 발견한 구조적 취약점 목록
3) 실제 수정한 파일/함수/로직
4) 어떤 재발 시나리오를 어떤 코드가 막는지
5) 아직 남아 있는 리스크
6) 추가로 권장하는 개선 사항
