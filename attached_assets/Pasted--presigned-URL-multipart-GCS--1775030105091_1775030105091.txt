현재 파일 업로드 시스템의 목표는 "업로드 지연 최소화"입니다.
지금 구조는 presigned URL 업로드가 실패하면 multipart 업로드로 내려가고, 거기서도 GCS 실패 시 DB base64 fallback로 저장됩니다.
하지만 실제 운영/배포 환경에서는 Object Storage sidecar 인증이 401이라, 대부분 느린 DB fallback 경로를 타고 있습니다.

이 구조를 "최대한 빠른 업로드" 기준으로 수정해줘.

## 핵심 목표
1. 느린 DB base64 fallback를 사실상 제거
2. presigned URL 직업 업로드를 최우선 경로로 고정
3. storage 인증 실패 시 느린 fallback 대신 빠른 실패(fail fast) 처리
4. 업로드 API 응답 시간 최소화
5. PDF 후처리는 반드시 비동기 분리
6. 서버 메모리 사용 최소화
7. 업로드 진행률과 상태 전이를 명확히 유지

---

## 현재 문제
- sidecar auth 401 때문에 presigned URL 경로가 자주 실패
- 결국 multipart → DB base64 fallback 경로로 감
- DB base64 저장은 대용량 파일에서 매우 느림
- multipart는 서버를 경유하므로 느리고 서버 리소스를 많이 씀
- PDF는 processing 전환이 있지만, 업로드 단계에서 불필요한 확인/처리가 길어질 여지가 있음
- direct-upload(base64 JSON)는 작은 파일만 허용되지만 구조적으로 느림

---

## 반드시 적용할 수정 사항

### 1) DB base64 fallback 제거 또는 강한 제한
현재:
- GCS 실패 → DB base64 저장

수정:
- 운영 환경에서는 DB base64 fallback 금지
- storage 업로드 실패 시 503 에러 반환
- 정말 필요하면 개발 환경에서만 1MB 이하 파일에 한해 임시 허용
- PDF, 이미지, 2MB 초과 파일은 절대 DB fallback 금지

예상 동작:
- presigned URL 실패 + multipart GCS 실패 → 즉시 실패 반환
- DB에 파일 원본 저장하지 않음

---

### 2) presigned URL 경로를 기본 경로로 고정
현재:
- presigned URL 발급 실패 시 multipart fallback

수정:
- presigned URL 업로드를 기본/우선 경로로 유지
- request-upload에서 presigned URL 발급이 안 되면, 바로 storage unavailable 에러 반환하도록 옵션 추가
- 운영 환경에서는 multipart fallback를 기본 비활성화
- multipart fallback는 관리자 플래그나 개발용 옵션으로만 허용

즉:
- 운영: presigned only
- 개발: 필요 시 multipart 허용

---

### 3) request-upload 단계 최적화
`POST /api/documents/request-upload` 를 최대한 가볍게 유지

수정:
- request-upload에서는 다음만 수행
  - 파일명/타입/크기 검증
  - storageKey 생성
  - presigned URL 생성
  - pending 문서 row 생성
- 불필요한 외부 체크 최소화
- presigned URL 발급 전에 sidecar health를 짧게 캐시해서 중복 확인하지 않도록 개선
- 인증 실패가 반복되면 일정 시간 동안 fast-fail 캐시 적용 (예: 30~60초)

예:
- storage auth 401 발생 시 매 요청마다 느리게 재검사하지 말고
- "현재 storage unavailable" 상태를 짧게 메모리 캐시해서 즉시 실패 반환

---

### 4) complete-upload 단계 가볍게 만들기
`POST /api/documents/complete-upload` 는 응답이 빨라야 함

수정:
- complete-upload에서는 파일 존재 확인만 최소한으로 수행
- 일반 파일:
  - 상태를 바로 ready 로 변경
- PDF:
  - 상태를 processing 으로 변경 후 즉시 응답
  - 압축/최적화는 백그라운드 작업에서 처리
- complete-upload 안에서 압축, 재다운로드, 재업로드 절대 금지

---

### 5) PDF 처리 완전 비동기화
수정:
- PDF 업로드 완료 직후:
  - 문서 상태 = processing
  - 사용자 응답 즉시 반환
- 백그라운드 잡에서:
  - 원본 PDF 다운로드
  - 압축/최적화
  - 결과 업로드
  - 상태 ready 변경
- 실패 시 failed 로 변경하고 에러 메시지 기록

즉, 업로드 API는 PDF 처리 완료를 기다리지 않음

---

### 6) multipart 경로 최소화
현재 multipart는 presigned 실패 시 자동 fallback

수정:
- multipart는 기본적으로 비활성화 가능하게 설정
- 운영 환경에서는 `UPLOAD_MULTIPART_FALLBACK=false` 기본값
- 개발 환경에서만 켤 수 있게 분기
- multipart 유지 시에도 memoryStorage 대신 stream 기반 업로드 검토
- 파일 전체를 RAM에 올리지 않도록 개선

---

### 7) direct-upload 더 강하게 제한
현재 direct-upload는 2MB 이하 전용, GCS only

수정:
- direct-upload는 가능하면 deprecated 처리
- 꼭 유지해야 하면:
  - 이미지/텍스트성 소형 파일만 허용
  - PDF 금지
  - 1MB 이하로 더 축소 검토
- base64 JSON 업로드는 신규 기능에서 사용하지 않게 정리

---

### 8) storage health / auth 상태 캐시
지연 최소화를 위해 storage 상태를 매 요청마다 무겁게 검사하지 않도록 수정

구현:
- sidecar auth check 결과를 짧게 캐시
- 예:
  - 성공 캐시 TTL: 60초
  - 실패 캐시 TTL: 30초
- `/api/health/storage` 에서 현재 캐시 상태, 마지막 체크 시간, 마지막 에러 이유 확인 가능하게 개선

---

### 9) 프론트엔드 업로드 전략 개선
프론트도 같이 정리

수정:
- 기본 업로드는 presigned URL PUT만 사용
- request-upload 실패 시 무조건 multipart로 재시도하지 말고,
  운영에서는 "저장소 일시 장애" 메시지 표시 후 사용자가 재시도하도록 변경
- 자동 재시도는 네트워크 오류 / PUT 실패에 대해서만 제한적으로 수행
- presigned URL 발급 실패(401/503)는 무한 fallback 하지 않음
- 진행률 표시 유지
- PDF는 업로드 완료 후 "처리 중" 상태를 보여주고 polling 또는 refetch

---

### 10) 문서 상태 흐름 명확화
상태 정의를 유지하되 더 엄격하게 정리

- pending: presigned URL 발급 완료, 아직 업로드 완료 전
- uploaded: 필요 시 중간 상태
- processing: PDF 후처리 중
- ready: 사용 가능
- failed: 업로드/처리 실패

권장:
- 일반 파일은 pending -> ready
- PDF는 pending -> processing -> ready
- 오류 시 failed

fail-upload 호출 시 pending 문서 정리가 확실히 되도록 수정

---

## 환경변수 / 플래그 추가
다음 설정을 추가해줘

- UPLOAD_PRESIGNED_ONLY=true
- UPLOAD_MULTIPART_FALLBACK=false
- UPLOAD_DB_FALLBACK=false
- STORAGE_HEALTHCACHE_SUCCESS_TTL_SEC=60
- STORAGE_HEALTHCACHE_FAILURE_TTL_SEC=30

개발 환경에서만 override 가능하게 해줘.
